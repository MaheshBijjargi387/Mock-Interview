# What is CI/CD?

Answer:
CI/CD stands for Continuous Integration and Continuous Delivery/Deployment.

CI means automatically building and testing code whenever developers push changes.
CD means automatically delivering or deploying the tested application to an environment.

# What is Jenkins?
->Jenkins is an open-source automation server used to implement CI/CD pipelines. It can automatically build, test, package, and deploy applications based on configured pipelines and triggers.

# What is a Jenkinsfile?
->A Jenkinsfile is a text file stored in the source-code repository that defines the stages and steps of a Jenkins CI/CD pipeline. Jenkins reads this file and executes the defined pipeline.

# What is GitHub Actions?
->  GitHub Actions is a CI/CD automation service provided by GitHub. It allows us to automatically build, test, and deploy our application when events such as a code push or pull request occur.

# What is a GitHub Actions Workflow?
->A GitHub Actions workflow is an automated process defiwned in a YAML file. It specifies when the workflow runs, what jobs should execute, and what steps those jobs should perform.

# What is the on section in GitHub Actions?
->The on section in a GitHub Actions workflow defines the events that trigger the workflow, such as a push, pull request, or manual execution.

# What is a Step in GitHub Actions?
->A step is an individual task inside a GitHub Actions job. A step can either execute a command using run or use an existing GitHub Action using uses.

# run vs uses
->run  → execute a command
uses → use an existing GitHub Action

# What is a Runner in GitHub Actions?
->A runner is a machine or environment where GitHub Actions executes a job. It can be GitHub-hosted, such as Ubuntu, Windows, or macOS, or it can be a self-hosted machine managed by the organization.

# What is actions/checkout in GitHub Actions?
->actions/checkout is a GitHub Action used to checkout the repository code onto the runner so that subsequent steps can build, test, or process the code.

# What is actions/setup-java in GitHub Actions?
->actions/setup-java is a GitHub Action used to set up a specific Java version and distribution on the GitHub Actions runner, so Java-based build and test commands can be executed.

# What is with?
->with is used to provide input parameters or configuration values to a GitHub Action. For example, actions/setup-java can use with to specify the Java version and distribution.
- name: Setup Java
  uses: actions/setup-java@v4
  with:
    java-version: '21'
    distribution: 'temurin'

# What is jobs and why do we use it in GitHub Actions?
->The jobs section defines the jobs in a GitHub Actions workflow. Each job contains steps and runs on a runner. Jobs can run independently or can depend on other jobs using needs.

# What is needs in GitHub Actions?
->needs is used to define dependencies between jobs in GitHub Actions. A job with needs waits for the specified job or jobs to complete successfully before it runs.

# What is a Secret in GitHub Actions?
->GitHub Actions Secrets are encrypted values used to securely store sensitive information such as passwords, tokens, and API keys. They can be accessed in workflows using the ${{ secrets.NAME }} syntax without hardcoding the sensitive value in the workflow file.

- name: Login to Docker Hub
  uses: docker/login-action@v3
  with:
    username: ${{ secrets.DOCKER_USERNAME }}
    password: ${{ secrets.DOCKER_PASSWORD }}

# What are GitHub Actions Artifacts?
->A GitHub Actions artifact is a file or collection of files generated by a workflow that can be stored and accessed after the workflow or job finishes. For example, a built JAR file, ZIP file, or test report can be uploaded as an artifact.

# What is the difference between an Artifact and a Docker Image?
->An artifact is a file produced by a CI/CD workflow, such as a JAR or ZIP, that can be stored or passed between jobs. A Docker image is a packaged application environment used to create and run containers.

# What is a GitHub Actions workflow file?
->A GitHub Actions workflow file is a YAML file stored in .github/workflows/ that defines the triggers, jobs, runners, and steps of a CI/CD workflow.

# What is a GitHub Actions Expression?
->A GitHub Actions expression uses the ${{ }} syntax to access workflow data, secrets, variables, and other contexts, or to evaluate conditions inside a workflow.

# What are Contexts in GitHub Actions?
->Contexts in GitHub Actions are predefined objects that provide information about the workflow, repository, event, secrets, jobs, and steps. They are accessed using ${{ }} expressions.

# What is env in GitHub Actions?
->env in GitHub Actions is used to define environment variables that can be used by workflows, jobs, or steps.

# What is the difference between env, secrets, and vars in GitHub Actions?
->env is used for environment variables, secrets are used for sensitive information like passwords and tokens, and vars are used for non-sensitive configuration values.

# What is if in GitHub Actions?
->if in GitHub Actions is used to conditionally run a job or step based on a specified condition.

# What are functions in GitHub Actions?
->GitHub Actions functions are built-in functions used inside expressions to check workflow      conditions, such as whether a previous step succeeded, failed, or was cancelled.
    Ex:success(),failure(),always(),cancelled()

# What is a matrix strategy in GitHub Actions?
->A matrix strategy allows us to run the same GitHub Actions job with different combinations of configurations, such as different programming language versions or operating systems.
strategy:
      matrix:
        java: ['17', '21']

# What is Caching in GitHub Actions?
->Caching in GitHub Actions stores reusable dependencies or files so future workflow runs can reuse them instead of downloading or generating them again, which makes the workflow faster.

# What is workflow_dispatch in GitHub Actions?
->workflow_dispatch is a GitHub Actions trigger that allows us to manually start a workflow from the GitHub Actions UI.

# What are Environments in GitHub Actions?
->GitHub Actions environments are used to manage different deployment environments such as development, staging, and production. They can have their own secrets and protection rules, such as required approvals.

# What is a Reusable Workflow in GitHub Actions?
->A reusable workflow is a GitHub Actions workflow that can be called by other workflows. It helps us reuse common CI/CD logic and avoid duplicate YAML code.

# What is the difference between a Reusable Workflow and an Action in GitHub Actions?
-> An Action is used to perform a specific reusable task, while a reusable workflow is used to reuse an entire workflow containing multiple jobs and steps.

# What is workflow_call in GitHub Actions?
->workflow_call is a GitHub Actions trigger that allows one workflow to call another workflow, making it reusable.

# What are Inputs and Outputs in a Reusable Workflow?
->Inputs are used to pass values into a reusable workflow, while outputs are used to pass values from the reusable workflow back to the calling workflow.

# What is continue-on-error in GitHub Actions?
->continue-on-error allows a workflow to continue even when a specified step or job fails. It is useful for non-critical tasks where failure should not stop the entire workflow.

# What is timeout-minutes in GitHub Actions?
->timeout-minutes sets the maximum time a job or step can run. If it exceeds that time, GitHub Actions stops the job or step.

# What is a Job Output in GitHub Actions?
->A job output is a value produced by one job that can be passed to and used by another job using needs.<job>.outputs.<output>.

# What is $GITHUB_OUTPUT in GitHub Actions?
->$GITHUB_OUTPUT is a special GitHub Actions file used to set outputs from a step so those values can be used by later steps or jobs.

# What is $GITHUB_ENV in GitHub Actions?
->$GITHUB_ENV is a special file provided by GitHub Actions that allows us to create or update an environment variable for later steps in the same job.

# What is $GITHUB_STEP_SUMMARY in GitHub Actions?
->$GITHUB_STEP_SUMMARY is a special GitHub Actions file used to add custom information and results to the job's Summary page.

# How do you build and push a Docker image using GitHub Actions?
->In GitHub Actions, we can automatically build a Docker image after code is pushed, log in to a container registry using secrets, and push the image to the registry.

# How does GitHub Actions deploy a Docker application to a server?
->GitHub Actions can deploy a Docker application by building and pushing the image to a container registry, connecting to the server through SSH, pulling the new image, stopping the old container, and starting a new container.

# What happens if a GitHub Actions workflow fails?
->When a GitHub Actions workflow fails, I first open the failed workflow, check the logs, identify the failed step, find the root cause, fix it, and rerun the workflow.

# How would you troubleshoot a Docker build failure in GitHub Actions?
->I would first check the GitHub Actions logs to identify the exact Docker error. Then I would check the Dockerfile, application build, build context, and .dockerignore. I would also reproduce the Docker build locally if possible, fix the issue, and rerun the workflow.

# What is the difference between push and pull_request triggers?
->push triggers a workflow when code is pushed to a branch, while pull_request triggers a workflow when a Pull Request event occurs. push is commonly used for CI or deployment, while pull_request is commonly used to validate code before merging.

# What is a Branch Filter in GitHub Actions?
->A branch filter in GitHub Actions is used to control which branches can trigger a workflow. We can use branches to include branches or branches-ignore to exclude them.

# What is a Path Filter in GitHub Actions?
->A path filter controls whether a GitHub Actions workflow runs based on which files or directories changed. It is useful for avoiding unnecessary workflow runs.

# What are GitHub Actions Permissions?
->GitHub Actions permissions control what a workflow can access or modify. We should give only the permissions required by the workflow to improve security.

# What is GITHUB_TOKEN in GitHub Actions?
->GITHUB_TOKEN is a temporary token automatically provided to GitHub Actions workflows for authenticating with GitHub. Its permissions can be controlled using the permissions setting.

# What is the difference between GITHUB_TOKEN and GitHub Secrets?
->GITHUB_TOKEN is an automatically generated temporary token used by workflows to interact with GitHub, while GitHub Secrets are securely stored sensitive values such as passwords, API keys, and SSH keys.

# What is a Self-Hosted Runner in GitHub Actions?
->A self-hosted runner is a machine managed by an organization that is registered with GitHub Actions and used to execute workflows instead of using GitHub-hosted runners.

# What is the difference between GitHub-hosted and self-hosted runners?
->GitHub-hosted runners are machines provided and managed by GitHub, while self-hosted runners are machines managed by the organization itself and registered with GitHub Actions.

# How do you upload an artifact in GitHub Actions?
->We use actions/upload-artifact to save files produced by a workflow, such as JAR files, ZIP files, or test reports, so they can be accessed or used later.

# What is the difference between Artifacts and Caching in GitHub Actions?
->Artifacts are used to store and share workflow outputs, while caching is used to reuse dependencies or files to make future workflow runs faster.

# What is concurrency in GitHub Actions?
->Concurrency in GitHub Actions is used to control multiple workflow runs and prevent unwanted runs from executing at the same time. It can also cancel an older run when a newer run starts.

# What is fail-fast in GitHub Actions?
->fail-fast controls whether other matrix jobs should be cancelled when one matrix job fails. By default, it is true.

# What is defaults in GitHub Actions?
->defaults is used to define default settings for run steps, such as the shell or working directory, so we don't have to repeat them in every step.
# What is working-directory in GitHub Actions?
->working-directory specifies the directory where a run command should execute.

# What is job-level vs step-level configuration in GitHub Actions?
->Job-level configuration applies to the whole job, while step-level configuration applies only to a specific step.

# What is a GitHub Actions deployment strategy?
->A deployment strategy defines how we release a new application version while controlling risk and downtime. Common strategies are rolling, blue-green, and canary deployment.
Rolling deployment → gradually replace old instances with new ones.
Blue-Green deployment → keep old and new versions running separately, then switch traffic to the new version.
Canary deployment → send the new version to a small percentage of users first, then increase it.


# What is the difference between a job and a stage in CI/CD?

Answer:

Stage: A major phase of the pipeline, such as Build, Test, or Deploy.
Job: A specific task or group of steps executed inside a stage.

# Your team has a CI/CD pipeline that builds and tests the application successfully, but the deployment stage fails.

What would you check to find and fix the problem?

Answer:
I would first check the deployment logs to identify the exact error. Then I would check:

Server/environment availability
Deployment credentials and permissions
Environment variables and secrets
Network connectivity
Application/artifact availability
Deployment configuration

# A developer pushes code to GitHub, but the CI/CD pipeline does not start.
->I would first check the pipeline trigger and branch configuration, then verify the webhook/event and workflow configuration to find why the pipeline was not triggered

# Your CI/CD pipeline successfully completes the build and test stages, but the deployment stage fails in production. How would you troubleshoot it?
->First, I would check the deployment logs to identify the exact error. Then I would verify server connectivity, credentials, deployment configuration, and application status. After fixing the issue, I would rerun the deployment and verify that the application is working.

# A developer pushes code to GitHub, but the CI/CD pipeline is not triggered automatically. How would you troubleshoot this issue?
->First, I would check whether the GitHub webhook is working. Then I would verify the pipeline trigger and branch configuration, repository permissions, and CI/CD logs. This helps identify why the push event is not triggering the pipeline

# Your CI/CD pipeline passes all tests, but after deployment, the application crashes in production. What would you check?
->"I would first check the production logs to find the error. Then I would verify environment variables, dependencies, database and external services. If the issue cannot be fixed quickly, I would rollback to the previous stable version.

# our CI/CD pipeline is running very slowly. A pipeline that normally takes 10 minutes now takes 30 minutes. How would you troubleshoot it?
->I would first identify which stage became slow by checking the pipeline logs. Then I would check the build, tests, dependencies, network, and runner resources. After finding the bottleneck, I would optimize that stage and rerun the pipeline

# A developer accidentally pushes a password or API key to the Git repository. The CI/CD pipeline starts automatically.
->"First, I would stop the pipeline and immediately revoke or rotate the exposed secret. Then I would remove it from the code, store it securely in CI/CD secrets, check whether it was used, and rerun the pipeline after fixing the issue.

# Your CI/CD pipeline deploys a new version to production, but the new version has a critical bug. Users are already facing problems.
->I would stop the deployment and rollback to the previous stable version to restore the application. Then I would investigate the issue, fix and test the bug, and deploy the corrected version.

# Your CI/CD pipeline passes in the development environment, but the application fails after deployment to production.
->I would compare the development and production environments, especially environment variables, configuration, dependencies, and database connections. Then I would check production logs to find the exact error, fix it, and redeploy

# Your CI/CD pipeline is deploying the application, but the deployment fails halfway through. Some servers have the new version, while others still have the old version.
->I would first check the deployment logs and identify which servers were updated. Then I would make all servers consistent by either rolling back or completing the deployment. Finally, I would verify that all servers are running the same version

# Your CI/CD pipeline runs successfully, but the Docker image is not being pushed to Docker Hub.
->I would first check the Docker push logs. Then I would verify the Docker Hub credentials, repository name, image tag, and repository permissions. After fixing the issue, I would rerun the pipeline and verify that the image is pushed successfully

# Your CI/CD pipeline is configured to deploy automatically whenever code is pushed to the main branch. A developer accidentally pushes unfinished code to main, and the pipeline starts deploying it to production.
->I would protect the main branch and require a pull request with code review and automated tests before merging. I would also configure the CI/CD pipeline so production deployment happens only after all required checks pass.

# Your CI/CD pipeline starts failing at the test stage after a developer pushes new code. The developer says, "The code works on my machine."
->I would first check the CI test logs. Then I would compare the CI environment with the developer's environment, especially runtime versions, dependencies, and environment variables. After reproducing and fixing the issue, I would run the pipeline again.

# Your CI/CD pipeline has CI and CD stages. The CI stage (build and test) passes successfully, but you want to make sure that only tested and approved code is deployed to production.
->I would run build and automated tests first. If they pass, I would create an artifact or Docker image and deploy it to staging. After successful staging tests and required approval, the same tested artifact would be deployed to production.

# Your CI/CD pipeline builds a Docker image successfully, but when the container starts in the deployment environment, it immediately stops.
->I would first check the container logs and exit code to find why it stopped. Then I would check the CMD or ENTRYPOINT, environment variables, ports, files, and dependencies. After fixing the issue, I would rebuild and redeploy the image.

# Your CI/CD pipeline has a build stage, test stage, and deployment stage. The build stage fails, but the test and deployment stages still start.
->I would configure dependencies between the stages so that test runs only when build succeeds, and deployment runs only when tests pass. If any required stage fails, the later stages should not execute.

# Your CI/CD pipeline deploys a new version to production successfully, but some users still see the old version while others see the new version.
->I would check all servers or containers behind the load balancer and verify their application versions. Then I would check load-balancer routing and caching. After making sure every instance has the new version, I would verify the application again.

# Your CI/CD pipeline deploys successfully, but the database migration fails because the new application version requires a new database column.
->I would check the migration logs and verify the database connection, permissions, and migration script. I would test the migration in staging first and make sure the database schema is compatible with the application before deploying to production.

# Your CI/CD pipeline has a production deployment approval step, but the person who normally approves deployments is unavailable. A critical bug fix needs to be deployed immediately.
->I would follow the organization's emergency deployment process and contact an authorized backup approver. I would make sure the fix passes the required tests, get the required approval, deploy it, and monitor the deployment.

# Your CI/CD pipeline deploys a new application version, but the health check starts failing immediately after deployment.
->I would check the health-check logs and application logs first. Then I would verify the port, configuration, database, and external services. If the application remains unhealthy, I would rollback to the previous stable version and fix the issue before redeploying.

# Your CI/CD pipeline is working correctly, but two developers push code to the same branch at nearly the same time. Both pipelines start, and one deployment overwrites the other.
->"I would prevent concurrent production deployments using a deployment lock or queue. I would also make the pipeline deploy a specific commit or artifact. If the wrong version is deployed, I would redeploy the correct version or rollback."

# Your CI/CD pipeline successfully deploys a new version, but after deployment the application's response time becomes very slow.
->I would check application logs and system resources first. Then I would check database performance, network calls, and compare the new version with the previous version. If the new deployment caused the slowdown, I would rollback and fix the issue before redeploying.

# Your CI/CD pipeline is running successfully, but the deployment job is using an old Docker image instead of the latest image that was just built and pushed.
->I would verify the image tag, registry push, and deployment configuration. Then I would check whether an old image is cached. I would pull the correct image and preferably use a unique tag such as the Git commit SHA to make sure the deployment uses the exact version.

# Your CI/CD pipeline deploys the application successfully, but the production server runs out of disk space after several deployments because old Docker images and containers are accumulating.
->I would first check disk usage and identify unused Docker images, containers, and volumes. I would safely clean up unused resources and configure regular cleanup and monitoring to prevent the disk from becoming full again

# Your CI/CD pipeline has multiple environments: Development → Staging → Production.A developer says the application works in Development but fails in Staging.
->I would first check the Staging logs. Then I would compare the Development and Staging environments, including variables, secrets, configuration, dependencies, and database connections. After fixing the issue, I would test it again before production deployment.

# Your CI/CD pipeline has 100 automated tests, but 5 tests fail randomly. Sometimes the pipeline passes and sometimes it fails, even though the code has not changed.
->I would identify the flaky tests and check their logs. Then I would run them repeatedly and investigate timing, network, test-data, or race-condition issues. After finding the root cause, I would fix the test or application problem and verify the pipeline again

# Your CI/CD pipeline is successful, but the production deployment takes 20 minutes, causing significant downtime for users.
->I would first identify the slow deployment step. Then I would use strategies like rolling or blue-green deployment to reduce downtime. I would also automate the deployment and keep a rollback option.

# Your CI/CD pipeline suddenly starts failing because the GitHub access token or cloud credential has expired.
->I would check the pipeline logs and confirm the authentication failure. Then I would replace the expired credential in the CI/CD secret manager, verify its permissions, and rerun the pipeline

# Your CI/CD pipeline successfully builds the application, but during the deployment stage it says:"Artifact not found."
->I would first verify that the artifact was created and uploaded successfully. Then I would check the artifact name, path, version, and permissions. After fixing the configuration, I would rerun the pipeline

# Your CI/CD pipeline is triggered successfully, but the job stays in "Queued/Pending" and never starts.
->I would first check whether the runner is online and available. Then I would verify its labels, resources, and current workload. If the runner has a problem, I would fix or restart it and run the job again.

# Your CI/CD pipeline successfully completes the build and tests, but the security scan fails because it finds a critical vulnerability in a dependency.
->I would check the security report and identify the vulnerable dependency. I would upgrade it to a safe version, run the tests and security scan again, and block production deployment if the critical vulnerability is still present.


# You need to deploy a new version of an application to production, but you don't want to send all users to the new version immediately.
->I would use a canary deployment. I would first send a small percentage of traffic to the new version and monitor it. If it works correctly, I would gradually increase the traffic. If problems occur, I would stop the rollout and return traffic to the previous version.

# Your team uses Terraform to create AWS infrastructure. You want Terraform changes to be managed through the CI/CD pipeline.
->"I would run Terraform format, validate, and plan in the CI stage. After review and approval, the CD stage would run Terraform apply. I would also securely manage the Terraform state and prevent concurrent changes."

# Your CI/CD pipeline takes 15 minutes because it downloads the same dependencies every time the pipeline runs.
->I would use pipeline caching to store dependencies between pipeline runs. This avoids downloading the same dependencies every time and makes the pipeline faster. I would also use a proper cache key so the cache is updated when dependencies change

# Your CI/CD pipeline finishes, but the development team does not know whether the deployment succeeded or failed.
->  I would configure the CI/CD pipeline to send notifications after the pipeline completes. The notification should contain the deployment status, commit, environment, and pipeline log link so the team can quickly respond to failures.

# Your CI/CD pipeline reports deployment successful, but after a few minutes users start experiencing errors.
->A successful deployment doesn't always mean the application is healthy. I would monitor logs, error rates, response time, and system resources after deployment. If the new version causes problems, I would rollback, investigate the root cause, and deploy the fixed version after testing.
